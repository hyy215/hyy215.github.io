Context Engineering：为大模型构建“正确的上下文信息” ​

在《大模型 Prompt 工程：从基础控制到推理、工具与自动优化》中，我们讨论了如何把任务说清楚。但当大模型进入多轮对话和 Agent 场景后，结果不再只取决于某一句 Prompt，还取决于模型在当前这一步究竟看到了什么。

这就是 Context Engineering（上下文工程） 要解决的问题：

在每次模型调用前，从不断变化的信息环境中选择、组织和维护完成当前任务所需的上下文。

图 1：Prompt Engineering 与面向 Agent 的 Context Engineering 对比。来源：Anthropic，Effective context engineering for AI agents。

本文聚焦“下一次模型调用应该看到什么”。至于工具如何执行、权限如何控制、任务如何调度，属于更外层的 Harness Engineering。

一、从邮件助手看：为什么只有 Prompt 还不够 ​

下面沿用 Philipp Schmid 的邮件助手场景，但把它展开成一个更接近实际系统的例子。

假设用户收到一封邮件：

明天有没有空，可以参加个会议吗？

如果模型只看到这句话，它并不知道用户的日历、时区、与发件人的关系，也不知道自己是否有权发送邀请。此时，即使 Prompt 写得很清楚，模型仍然只能猜测：

谢谢你的消息。明天我有空。请问你方便什么时间？

问题不在语言表达，而在决策所需的信息缺失。要可靠地处理这封邮件，应用需要在调用模型前组织出一组与当前任务直接相关的上下文：

  • 任务目标：理解会议邀请，生成回复草稿，并提供真实可用的候选时间；
  • 已验证事实：日历查询结果、用户时区和现有会议安排；
  • 用户偏好与沟通背景：常用会议时段，以及与发件人以往的沟通风格；
  • 行为边界：不得虚构日程；未经用户确认，不得发送邮件或创建邀请；
  • 工具接口：本轮可以使用哪些工具，以及各工具的参数、返回值和错误信息；
  • 输出契约：返回回复草稿、候选时间，并明确是否需要用户确认。

模型实际收到的不是“全部系统数据”，而是应用从这些信息中挑出的一个上下文包。这个场景也说明了上下文工程的两个特点：

  1. 上下文不是一次性写好的长 Prompt，而是每轮重新构建的；
  2. 目标不是让模型看到最多信息，而是让它看到完成当前步骤所需的高价值信息。

二、Context Engineering 是什么 ​

1. Context 包含哪些内容 ​

Philipp Schmid 对 Context 的解释是：它不只是一条发送给大模型的 Prompt，而是模型生成回答前能够看到的全部信息。常见内容包括：

  • Instructions / System Prompt：定义模型行为的指令、规则和示例；
  • User Prompt：用户当前提出的问题或任务；
  • State / History：当前会话及此前的用户与模型消息，也可视为短期记忆；
  • Long-Term Memory：跨会话保存的用户偏好、项目摘要或其他长期信息；
  • Retrieved Information / RAG：从文档、数据库或 API 动态获取的外部信息；
  • Available Tools：模型可以调用的函数或工具定义；
  • Structured Output：对模型输出格式的定义，例如 JSON Schema。

这些内容并不是互相隔离的固定技术层，而是 Philipp Schmid 为了说明 Context 范围所采用的解释框架。

图 2：模型生成回答前可能接收的 Context 组成。来源：Philipp Schmid，The New Skill in AI is Not Prompting, It's Context Engineering。

2. Context Engineering 是什么 ​

LangChain 在《The rise of context engineering》中的定义是：

Context Engineering 是构建动态系统，以合适的格式向大模型提供正确的信息和工具，使模型有可能完成任务。

这个定义包含五个要点：

  1. 它是一套系统：上下文可能来自应用开发者、用户、之前的交互、工具调用和其他外部数据，需要由系统把这些来源组织起来；
  2. 它是动态的：上下文会随任务推进而变化，最终发送给模型的 Prompt 也需要动态构建，而不是预先写死；
  3. 需要正确的信息：缺少完成当前步骤所需的信息时，模型无法凭空知道现实状态；
  4. 需要正确的工具：当输入本身不足以完成任务时，模型需要通过工具查询信息或执行操作；
  5. 格式同样重要：信息和工具参数的表达方式会影响模型能否正确理解和使用它们。

因此，判断上下文是否合适，可以先问：

在当前提供的信息、工具和表达形式下，模型是否具备完成任务的条件？

三、Context 为什么会失效 ​

长上下文并不等于模型能稳定使用其中的每条信息。Lost in the Middle 在多文档问答和键值检索实验中发现，相关信息所处的位置会显著影响模型表现，信息位于长上下文中部时尤其容易被忽略。这类研究说明：上下文窗口容量是上限，不是有效利用所有内容的保证。

从上下文质量来看，常见问题可以归纳为四类。

1. 信息不足：模型只能猜 ​

如果邮件助手没有查询日历，它就无法可靠判断用户明天是否有空。缺少关键信息时，模型可能：

  • 用常识填补业务事实；
  • 把可能性写成确定结论；
  • 选择一个看似合理、实际不可执行的动作。

首先应检查任务是否缺少必要事实、工具或成功标准，而不是立即增加更复杂的推理提示词。

2. 信息错误或过时：错误被持续继承 ​

错误信息一旦被写入历史、摘要或长期记忆，后续调用可能继续把它当作事实。例如：

用户已确认会议安排在周五。

如果这句话其实只是模型的建议，却在摘要中被写成“已确认”，后续提醒、邀请和回复都会建立在错误状态上。

实际系统应区分：

  • 用户明确确认的事实；
  • 工具查询得到的事实；
  • 模型生成的建议或假设；
  • 需要重新验证的过期信息。

3. 信息过多或无关：重点被稀释 ​

把完整邮件历史、所有联系人资料、全部工具定义和大段日志一次性塞给模型，会同时增加 token、延迟和干扰。

常见表现包括：

  • 模型引用了与当前任务无关的旧信息；
  • 工具过多，模型选错工具；
  • 回答围绕背景展开，却没有完成当前任务；
  • 关键约束埋在上下文中部，没有被稳定遵循。

4. 信息冲突：模型无法稳定选择 ​

冲突可能来自不同来源：

  • 用户档案写着“不要安排上午会议”，但本轮用户明确要求上午；
  • 旧摘要写着“会议在周五”，最新日历结果却显示会议已取消；
  • 两份业务规则对审批条件的描述不一致；
  • 同一优先级的指令分别要求“必须详细解释”和“只允许一句话”。

解决冲突不能只靠调整文字顺序。系统应先区分“谁有权提出要求”和“哪个来源更能代表现实状态”，再分别定义优先级、更新时间和覆盖规则。例如：

text
指令与行为约束：
系统与安全策略
  > 本轮用户明确要求
  > 长期用户偏好
  > 历史摘要中的旧要求

事实与现实状态：
已验证的实时工具结果
  > 当前任务中已确认的状态
  > 带有来源和时间的长期记忆
  > 历史摘要

四、四类上下文管理策略 ​

LangChain 将常见的 Agent 上下文策略归纳为 Write、Select、Compress 和 Isolate。它们不是严格互斥的架构层，而是可以组合使用的四类操作。

图 3：Write、Select、Compress 和 Isolate 四类上下文管理策略及其常见实现。来源：LangChain，Context Engineering。

1. Write Context：把重要信息持久化 ​

Write 解决的是“重要信息不能只存在于当前窗口”。

会话内状态 ​

适合保存当前任务的：

  • 目标与成功标准；
  • 已确认事实；
  • 已完成步骤和待办事项；
  • 工具调用结果的关键结论；
  • 仍需验证的假设。

实现可以是运行时状态字段、任务清单、检查点或文件。Anthropic 在其多 Agent 研究系统中披露，LeadResearcher 会把计划保存到 Memory，以免上下文超过 20 万 token 被截断后丢失计划。

跨会话记忆 ​

适合保存相对稳定、未来仍可能有用的信息，例如用户偏好和项目背景。

Reflexion 将任务反馈转化为文本反思并保存在情节记忆中；Generative Agents 则记录经历、生成更高层反思，并在后续规划时动态检索。这些研究说明了“写入—整理—检索”的基本模式，但不意味着生产系统应自动保存模型生成的所有内容。

持久化上下文的质量控制：

  • 为记忆记录来源、更新时间和适用范围；
  • 将“事实”“偏好”“建议”“模型推测”分开存储；
  • 对敏感信息设置保存期限和删除机制；
  • 不把模型内部推理过程当作必须持久化的业务事实。

2. Select Context：只取当前步骤需要的内容 ​

Select 解决的是“候选信息很多，但本轮只能选择一部分”。

常见做法包括：

  • 固定加载少量稳定规则；
  • 根据任务类型选择工具；
  • 使用关键词、向量检索或知识图谱召回候选信息；
  • 用权限、时间、来源和业务范围过滤结果；
  • 对候选结果重排序，再取前若干条进入上下文。

工具选择也可以使用检索。RAG-MCP 在论文设定的 MCP 工具选择基准中，将准确率从 13.62% 提升到 43.13%，同时减少了超过一半的 Prompt token。这个结果说明“先检索工具、再向模型暴露少量候选”可能有效，但不能直接推导为任意模型、任意工具集都能获得三倍提升。

选择结果的质量控制：

  • 只追求精确率可能漏掉必要信息，因此要同时评估召回率；
  • 检索结果必须保留来源，而不是只给模型一段失去出处的文本；
  • 实时状态优先直接查询，不应只依赖向量库中的旧副本；
  • 当任务风险较高时，关键事实应通过确定性查询或二次验证获得。

3. Compress Context：保留结论，减少重复 ​

Compress 解决的是“信息仍然重要，但原始形式太长”。

两种基本方式是：

  • 总结（Summarization）：把长历史提炼成更短的状态；
  • 裁剪（Trimming）：直接删除已经无关、可重取或重复的内容。

对于需要跨多轮保持任务状态的场景，可以使用类似下面的摘要结构。具体字段应根据任务需求和评测结果确定：

yaml
goal: 当前目标
constraints:
  - 必须遵守的约束
confirmed_facts:
  - 已确认事实、来源和时间
decisions:
  - 已做出的决定及原因
open_items:
  - 未解决问题
source_pointers:
  - 可重新读取的文件、查询或链接

Claude Code 的官方文档说明，自动压缩（auto-compaction）会在会话接近上下文限制时总结历史，以释放上下文空间。

压缩结果的质量控制：

  • 总结会丢失细节，需要测试哪些字段必须保留；
  • 原始数据可重新查询时，优先保留引用而不是复制全文；
  • 工具返回的大段日志通常可以裁剪，但错误码、关键参数和验证结果应保留；
  • 摘要本身也可能写错，应允许回看原始记录。

4. Isolate Context：让不同任务互不干扰 ​

Isolate 解决的是“某些信息不应该同时出现在同一个模型窗口中”。

常见方式包括：

状态隔离 ​

运行时状态可以包含日历结果、权限信息、审计记录等多个字段，但每一轮只向模型暴露完成当前步骤需要的部分。隐藏字段不是“模型记住但暂时不看”，而是根本没有进入本轮模型输入。

环境隔离 ​

大型文件、音视频、数据库结果可以留在外部环境中。模型先通过工具获得文件路径、字段统计或局部查询结果，必要时再继续读取，而不是一次加载全部内容。

子 Agent 隔离 ​

把相对独立的子任务分给不同 Agent，每个 Agent 使用独立上下文，主 Agent 只接收经过压缩的结果。这适合可并行、依赖较少的研究任务，不适合所有参与者都必须共享完整状态的任务。

Anthropic 披露的研究系统中，普通 Agent 的 token 使用量约为聊天的 4 倍，多 Agent 系统约为聊天的 15 倍。这是该产品和工作负载下的观测值，不是通用成本公式；它更重要的启示是：上下文隔离可能提高任务覆盖，但会增加 token、协调和评估成本。

五、邮件助手的完整上下文构建过程 ​

回到开头的会议邀请。一个可落地的实现不应先把全部邮箱和日历塞给模型，而应从任务所需事实倒推上下文。

1. 明确成功标准 ​

这次任务的成功标准可以是：

  • 不虚构用户的空闲时间；
  • 给出至少一个来自实时日历的候选时段；
  • 保持与发件人关系相符的语气；
  • 未经用户确认，不发送邮件或会议邀请。

2. 构建本轮上下文包 ​

应用可以先通过确定性代码查询日历和权限，再组装类似下面的数据：

4. 下一轮如何更新 ​

如果用户回复“可以，发出去吧”，系统再：

  1. 重新检查候选时间是否仍然可用；
  2. 把用户确认写入任务状态；
  3. 暴露发送邮件和创建邀请所需的工具；
  4. 执行后把真实工具结果写回状态；
  5. 向用户报告成功或失败，而不是根据模型预测结果。

这样，每一轮调用只向模型提供当前步骤所需且经过验证的信息；新的用户确认和工具结果再写回任务状态，成为构建下一轮上下文的依据。
