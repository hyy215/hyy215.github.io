理解 Graph Engineering：用可执行图组织 Agent 工作流 ​

上一篇《理解 Loop Engineering：从逐步提示 Coding Agent 到设计可收敛的反馈循环》讨论了如何让执行过程根据反馈持续推进，以及如何判断循环应当继续还是停止。

不过，当一个任务包含多个工作单元时，单个反馈循环已经不足以描述它们之间的关系：

  • 一些工作单元可以并行执行；
  • 一些必须等待一个或多个前置结果；
  • 不同分支的结果需要在后续阶段汇合；
  • 中间结果还可能动态生成新的工作单元。

这时，还要明确工作单元如何产生、彼此如何连接，状态如何在它们之间传递，分支结果如何汇合，以及整个工作流在什么条件下结束。

Graph Engineering 关注的，正是如何将这些关系显式组织为可执行的图。

一、什么是 Graph Engineering ​

按照 LangGraph 团队的描述，图为定义 Agent 工作流提供了一种具体结构：节点执行工作，边决定下一步。

据此，本文采用以下工作定义：

Graph Engineering 是将 Agent 系统中的工作单元表示为节点，并明确节点之间的依赖关系、状态如何传递、执行如何转移，以及流程在什么条件下终止，从而形成可执行的图。

图 1：工作单元通过边连接；执行结果决定后续路径，不同分支也可以在之后重新汇合。

二、什么时候适合用图组织 Agent 工作流 ​

并不是所有 Agent 任务都适合组织成图。根据 LangGraph 团队的总结，图更适合结构可以预判的工作流：设计者能够事先说明主要阶段和允许的路径，并明确哪些环节允许模型作出选择，哪些环节必须遵循预先设定的确定性逻辑。

例如：

  • 客服 Agent 先判断问题类型，再回答或转交人工；
  • 编码 Agent 在提出修改前检查仓库；
  • 合规流程在执行外部操作前获得批准。

在这些场景中，具体输出和分支选择仍要到运行时才能确定，但工作流的整体结构可以预先定义。Graph 的作用，是明确已知的结构，同时在真正需要判断的环节保留运行时选择的空间。

反之，如果连任务如何规划、如何委派工作以及沿哪些路径探索都难以事先确定，预定义的图反而可能限制 Agent。LangGraph 团队认为，这类任务更适合使用 Deep Agents 一类的 Agent Harness（Agent 运行框架）。

三、Graph Engineering 包含哪些元素 ​

节点、边和状态构成 Agent Graph 的基本元素；在此基础上，执行路径可以形成循环，也可以在运行时动态展开。

节点：执行工作的单元 ​

在 LangGraph 团队的描述中，节点可以是：

  • 确定性代码；
  • 单次 LLM 调用；
  • 工具调用；
  • 带有内部循环的完整 Agent。

此外，Josh C. Simmons也将人视为一种节点：人工审批可以作为流程中的一个节点。

无论由代码、模型、Agent 还是人来执行，节点都应具有清晰的工作边界。Simmons 给出的判断是：一个好的节点只做一件事，可以独立测试，也能在不改动其他部分的情况下替换。

确定节点的工作边界后，还要根据工作性质选择合适的执行方式。例如，在 LangGraph 团队给出的知识库 Agent 示例中，模型推理只放在能够发挥价值的环节，其余控制与编排工作由代码完成。这样既能保留模型处理开放问题的能力，也能降低成本和延迟，提高系统的可预测性。

边：决定接下来发生什么 ​

按照 LangGraph 团队的描述，边表示节点之间的执行关系，决定一个节点完成后哪些节点会被触发。根据后续路径是否预先确定，可以分为：

  • 确定性边：节点完成后，沿预先定义的路径进入后续节点；
  • 条件边：运行时根据节点的执行结果、当前状态或外部信号选择后续路径。

状态：记录并共享执行所需的信息 ​

在 LangGraph 的定义中，State（状态）是表示应用当前快照的共享数据结构。节点读取状态以完成工作，并返回对状态的更新；条件边也可以依据状态中的信息选择后续路径。

状态中具体保存哪些内容，取决于工作流本身。LangGraph 的设计指南建议，需要跨步骤保留的信息应写入状态；能够从已有数据推导出的信息则无需保存，在需要时重新计算即可。

Loop：节点内部与节点之间的循环 ​

Loop 不是 Graph 的替代方案。从结构上看，Loop 本身就是一种有向循环图，也可以作为更大 Graph 的局部结构。以节点为边界，可以观察到两种循环：

  • 节点内部：循环可以封装在单个节点中。例如，当节点本身是 Agent 时，它可以反复调用模型和工具，直到满足退出条件；
  • 节点之间：循环可以跨越多个节点，由边将执行路径导回已经执行过的节点。例如，检查未通过后，流程可以返回前面的 Agent 节点。

图 2：Agent 作为工作图中的一个节点，内部可以运行自己的循环；检查未通过时，执行路径也可以返回该节点。

动态转移：在运行时确定后续工作 ​

Graph 的节点和静态拓扑通常在设计阶段定义，但运行时需要处理的任务数量可能取决于当前输入，无法提前确定。针对这种情况，节点可以生成若干子任务，并通过动态转移将每个子任务及其独立输入发送给工作节点处理。LangGraph 团队将 Map-reduce 作为典型例子：

  • 根据当前输入生成若干可以独立处理的子任务；
  • 将这些子任务分别交给同一工作节点处理；
  • 汇总各个运行实例返回的结果。

图 3：系统根据当前输入生成数量不定的子任务，并以不同输入调用同一工作节点的多个运行实例，最后汇总各个实例的结果。

四、图不会自动带来可靠性 ​

Graph 可以明确节点、边和状态的职责及其关系，但结构清楚并不等于系统已经可靠。节点仍可能给出错误结果，执行过程可能因故障而中断，循环和动态分支也可能使执行次数及资源消耗持续增长。因此，还需要保存执行状态、验证节点结果，并为执行过程设置资源限制。

保存执行状态并支持故障恢复 ​

运行时间较长的 Agent 任务可能因为节点报错、人工暂停或其他原因而中断。如果系统没有保存中间状态，恢复时就只能从头执行，已经完成的模型调用、工具调用和其他工作也会被重复执行。

LangGraph 使用 Checkpointer自动保存工作图的执行状态。理解这个机制需要区分三个概念：

  • Thread：同一任务的持续执行记录，由 thread_id 标识，用于组织该任务产生的 Checkpoint；
  • Super-step：一次节点调度批次。当前状态确定后，所有已经具备执行条件的节点会在这一批次中运行；串行流程中通常只有一个节点，并行分支中则可以有多个节点；
  • Checkpoint：在 Super-step 边界保存的状态快照，记录当时的图状态和接下来要执行的节点。

任务中断后，系统可以通过同一个 thread_id 找到最近保存的 Checkpoint，并从相应位置继续。如果同一 Super-step 中只有部分节点失败，已经成功完成的节点结果会被保留，恢复时只需继续处理尚未完成或执行失败的部分。

图 4：LangGraph 在每个 Super-step 保存图状态及相关元数据，并将多个 Checkpoint 组织在一个 Thread 中。来源：LangChain，Checkpointers。

Checkpoint 解决的是“执行中断后能否继续”的问题，但它不会判断节点保存的结果是否正确。如果错误结果已经写入状态，恢复执行时仍会继续使用这些结果。因此，保存执行状态只能提高流程的可恢复性，结果是否可信还需要通过后续的验证机制判断。

使用外部证据验证结果 ​

Bouchard引用 Carlos Perez 的观点指出：即使设置多个审核 Agent，如果它们使用同一种模型，并读取同一份有误的上下文，也可能得出一致但错误的结论。因此，增加审核节点并不等于获得独立验证。

验证还需要引入 Agent 系统之外的信号，例如实际运行的测试结果、真实的业务结果或领域专家的判断。Graph 可以组织这些证据的生成与检查流程，但图结构本身不能证明结果正确；最终结论仍要由这些外部信号检验。

把资源限制纳入执行过程 ​

Simmons建议将 Token 用量、费用和实际运行时间记录在状态中，并在执行路径沿边进入下一节点时检查预算。一旦某项资源消耗达到设定上限，系统就可以停止执行，避免循环或动态分支在缺少约束的情况下持续消耗资源。

五、用图理解 Claude Research 与 GPT Researcher ​

本节通过两个研究型 Agent 工作流，观察 Graph 如何组织规划、分工、研究和汇总：

  • Anthropic 于 2025 年公开介绍了 Claude Research 的生产架构，其研究路径与 Subagent 数量可以动态变化；
  • GPT Researcher 仓库当前保留了一个 LangGraph 多 Agent 示例，其主要阶段和返回路径已经预先定义。

下文仅分析公开资料所描述的这两个工作流，不代表两个项目当前的所有实现。

Claude Research：用图梳理动态工作关系 ​

Anthropic 将 Claude Research 描述为 orchestrator-worker 多 Agent 系统。沿着官方图中的执行顺序，可以将整个过程分成五步：

  1. 创建并初始化 LeadResearcher

    系统收到问题后创建 LeadResearcher。LeadResearcher 制定研究策略，并将计划保存到 Memory。

  2. 动态创建研究工作

    LeadResearcher 根据问题创建若干 Subagent，并为它们分配不同的研究方向。Subagent 数量不固定，可以根据任务和中间发现继续增加。

  3. Subagent 独立执行内部循环

    每个 Subagent 在自己的上下文中反复搜索、评估工具结果，并将研究发现返回 LeadResearcher。

  4. 根据结果选择后续路径

    LeadResearcher 汇总各个 Subagent 的发现。如果信息不足，就调整策略或创建新的 Subagent；如果信息充分，就退出研究循环。

  5. 处理引用并返回结果

    研究结束后，材料被交给 CitationAgent 定位引用，最终由系统返回带有引用的研究结果。

图 5：Claude Research 的 LeadResearcher 创建 Subagent 并汇总研究结果，在信息充分后将结果交给 CitationAgent 处理引用。来源：Anthropic，How we built our multi-agent research system。

Anthropic 在文章附录中还提出了三项补充建议，其中两项与前文讨论的状态管理和跨节点产物交接直接相关：

  • 评估最终状态：对于会在多轮执行中持续修改状态的 Agent，评估重点应放在最终状态是否正确，而不是是否遵循预先设定的每一步。流程较复杂时，可以设置阶段性验收点，检查相应的状态变化是否已经完成。
  • 通过外部存储交接产物：对于代码、报告和数据可视化等篇幅较大的结构化产物，可以由 Subagent 直接保存到文件系统等外部存储中，只将引用返回协调者，从而减少多阶段传递造成的信息损失和 Token 消耗。

GPT Researcher 的 LangGraph 多 Agent 示例 ​

GPT Researcher 仓库中的 LangGraph 多 Agent 示例，将规划、研究、审核、修订和发布组织成一张图。

沿着公开架构图中的执行顺序，可以将整个过程分成五步：

  1. 完成初步研究

    初步研究节点使用 GPTResearcher 搜集与任务相关的资料，为后续规划报告结构提供依据。

  2. 规划并确认报告结构

    Editor 根据初步研究拟定报告大纲。启用人工反馈时，Human 可以检查大纲；如果提出修改意见，流程就返回 Editor 重新规划。

  3. 并行研究各个主题

    每个大纲主题对应一条独立的研究分支。Researcher 完成深入研究并生成草稿，Reviewer 随后检查草稿；如果草稿未通过，Revisor 根据反馈修改，再交给 Reviewer 复核。不同主题的研究可以并行进行。

  4. 汇总研究结果

    各条研究分支完成后，Writer 将内容合并为完整报告，并补充引言、结论和参考资料。

  5. 发布报告

    Publisher 将最终报告输出为 PDF、DOCX 和 Markdown 等格式。

图 6：GPT Researcher 先规划报告结构，再围绕各个主题并行研究和修改，最后汇总并发布报告。来源：GPT Researcher，LangGraph x GPT Researcher。

与 Claude Research 根据中间发现继续创建 Subagent 不同，这个流程的主要阶段和返回路径已经预先定义；运行时的变化主要来自大纲包含多少个主题，以及草稿是否需要进入修订循环。

六、结论 ​

归根结底，Graph Engineering 是一种显式组织和编排 Agent 工作流的方式。它不是预先写死所有步骤，而是在明确工作关系的同时，为循环、分支和动态任务保留运行时变化的空间。是否采用它，取决于任务中的这些关系是否需要被明确表示为图。
