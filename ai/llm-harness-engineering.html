理解 Harness Engineering：Coding Agent 如何在系统中可靠工作 ​

当 Coding Agent 不再只是完成一次代码修改，而是开始承担耗时更长、涉及范围更广的软件工程任务时，仅靠模型能力已不足以保证结果可靠。如果缺少合适的工程环境和约束，Agent 仍可能：

  • 在长任务中丢失进度，或者过早宣布完成；
  • 没有经过充分验证，就对自己的实现作出过于乐观的判断；
  • 无法获取未被显式记录的项目知识，也难以持续遵守工程约束。

这些问题并非只由模型能力决定，还取决于 Agent 所处的系统：它能看到哪些信息、可以执行哪些操作、如何判断任务是否完成、能获得怎样的反馈，以及需要遵守哪些工程边界。

本文以 Coding Agent 为讨论对象，重点关注使用者围绕具体项目建立的用户 Harness。本文所说的 Harness Engineering，是指对引导信息、执行环境、工程约束以及验证和反馈机制进行设计与持续维护，使 Agent 能够在特定任务和系统中更可靠地工作，并在发现偏差后及时修正。

一、Harness Engineering 是什么 ​

Birgitta Böckeler 在 Harness engineering for coding agent users 中，用三个同心层次说明 Coding Agent 语境下 Harness 的不同边界：

  • 模型：提供推理和生成能力；
  • 构建者 Harness（Builder Harness）：由 Coding Agent 的构建者提供，包括系统提示词、代码检索和编排机制等；
  • 用户 Harness：由使用者围绕具体项目建立，包括项目知识、运行环境、工程约束和验证反馈。

三者的关系如下图所示：

图 1：Coding Agent 的三层边界。来源：Birgitta Böckeler，Harness engineering for coding agent users。

Böckeler 进一步根据作用方向，将用户 Harness 中的控制分为两类：

  • Guides（前馈控制）：在 Agent 行动之前提供目标、规则和参考信息；
  • Sensors（反馈控制）：在 Agent 行动之后观察结果，并将偏差反馈给 Agent。

Guides 提高 Agent 第一次做对的概率，Sensors 则帮助它发现并修正错误。两者结合，构成前馈引导与反馈纠偏相互配合的控制闭环。

图 2：用户 Harness 的 Guides、Sensors 与自我修正循环。来源：Birgitta Böckeler，Harness engineering for coding agent users。

为了进一步说明这些控制如何发挥作用，Böckeler 又从执行方式上将 Guides 和 Sensors 分为两类：

  • 计算型控制：由确定性工具执行。作为 Guides，常见形式有语言服务器、CLI、脚本或代码转换工具（codemod）；作为 Sensors，常见形式有测试、Lint、类型检查或结构分析。这类控制通常执行较快，结果也相对确定；
  • 推断型控制：依靠模型进行语义判断。作为 Guides，常见形式有工程原则、规则、参考文档或操作指南；作为 Sensors，常见形式有 AI Code Review 或 LLM-as-a-judge。这类控制通常执行较慢、成本较高，结果也存在更多不确定性。

快速的计算型控制可以伴随 Agent 的每次修改运行，成本较高的推断型控制则需要结合实际收益按需执行。原文用下面这张图举例说明，如何根据成本和执行速度，将不同类型的 Guides 和 Sensors 安排在代码变更生命周期的不同阶段：

图 3：变更生命周期中的前馈与反馈控制示例。来源：Birgitta Böckeler，Harness engineering for coding agent users。

用户还需要持续调整这套机制。如果同一类问题反复出现，就应改进相应的 Guides 或 Sensors，降低这类问题再次发生的概率，或者让问题更早暴露。

二、用户 Harness 如何解决实际工程问题 ​

下面结合 OpenAI 的 Codex 工程实践，以及 Anthropic 的跨上下文长任务实验和长任务应用开发实验，说明用户 Harness 如何帮助 Coding Agent 获取并延续任务上下文，协调规划、实现与评价，并将反复出现的问题转化为可以持续维护的工程机制。

1. 上下文与任务连续性 ​

长任务中的上下文问题主要有两个：Agent 如何找到当前任务所需的项目知识，以及任务跨越多个上下文窗口后，如何保持工作连续性。

项目知识：将代码仓库作为系统记录 ​

为了让 Agent 找到当前任务所需的项目知识，可以将代码仓库作为系统记录。与其把所有信息塞进一个巨大的 AGENTS.md，不如只让它承担目录作用，再将架构、产品规格、执行计划、决策记录和技术债放入结构化的 docs/。这些资料与代码一起版本化，Agent 从简短入口开始，只在需要时继续读取相关内容。

任务连续性：将项目状态保存在对话之外 ​

对于跨越多个上下文窗口的复杂任务，需要将执行计划、当前进度、历史决策和技术债等项目状态保存在外部文件与 Git 历史中。

Anthropic 的跨上下文长任务实验使用以下三类记录保存任务状态：

  • feature_list.json：记录完整的功能清单、端到端验证步骤及通过状态

  • claude-progress.txt：记录本次会话完成的工作、当前状态和下一步安排；

  • Git：通过增量提交记录代码变化，并保留可以恢复的历史状态。

三者共同构成跨会话的交接机制。新的会话先读取 feature_list.json，选择一项尚未完成的功能，再通过 claude-progress.txt 了解当前状态和下一步工作，并结合 Git 日志确认近期的代码变化。

完成修改后，Agent 更新功能状态和进度文件，并使用描述清楚的 Git 提交保存代码。会话结束时，还要让工作环境保持可交接的整洁状态（clean state）：代码不存在严重问题、结构有序，并留有必要的说明，使后续 Agent 能够直接继续开发。如果修改引入问题，也可以通过 Git 回退到此前可用的状态。

上下文焦虑：必要时重置上下文 ​

早期使用 Sonnet 4.5 时，模型存在明显的 Context Anxiety：随着上下文逐渐填满，它可能失去连贯性，或者因为认为即将达到上限而提前收尾。上下文压缩虽然会将较早的对话整理成摘要，让模型基于精简后的历史继续工作，但它仍然沿用原有上下文，无法像新会话那样提供一个完全干净的起点，因此不能彻底解决上下文焦虑。

为此，Harness 引入了 Context Reset：清空当前上下文并启动新的 Agent，再通过结构化交接材料传递上一阶段的状态和下一步工作。

备注： 换成 Opus 4.5 后，Context Anxiety 已大幅减少。文章作者因此移除了 Context Reset，让 Agent 在一次连续会话中完成整个构建过程，并由 Claude Agent SDK 的自动压缩机制处理不断增长的上下文。

2. 规划、实现与评价 ​

为什么分成三个 Agent ​

Anthropic 的长任务应用开发实验观察到，直接让一个 Agent 完成整个应用时，容易出现两个问题：用户只提供一至四句话的简短需求时，Agent 容易立即开始编码，导致最终实现的产品范围小于预期；完成实现后，Agent 往往还会高估自己的成果，即使结果在人类看来明显不够理想。

为此，Anthropic 将规划、实现和评价交给三个不同的 Agent：

  • Planner：将简短需求扩展为完整产品规格，明确产品范围和高层技术设计；
  • Generator：读取产品规格并负责具体实现；
  • Evaluator：独立检查 Generator 的实现是否符合产品规格和评价标准。

不过，Planner 只确定要交付什么，不提前规定过细的技术实现。实验作者认为，如果 Planner 在细节上判断错误，这些错误可能沿着产品规格进入后续实现。

之所以将 Generator 与 Evaluator 分开，是因为 Generator 在完成实现后，往往难以严格审视自己的成果。将评价职责交给独立的 Evaluator，也便于单独校准其判断标准。

实际运行过程 ​

在使用 Opus 4.5 的版本中，三个 Agent 按照以下流程协作：

  1. Planner 将简短需求扩展为完整产品规格。
  2. Generator 将构建过程拆成多个实现轮次（Sprint），每个 Sprint 从产品规格中选择一项功能。
  3. 编码前，Generator 与 Evaluator 先协商验收约定（Sprint Contract），明确当前 Sprint 的实现范围和验收标准。Generator 提出本轮要实现的内容和验证方法，Evaluator 再检查它们是否符合产品规格、能否实际验证。双方达成一致后，Generator 才开始编码。
  4. Generator 按照验收约定完成功能并进行自我检查，再将结果交给 Evaluator。
  5. Evaluator 评价实现结果，并将发现的问题反馈给 Generator 继续修改。

三个 Agent 通过文件传递信息。产品规格、验收约定和评价结果都会保存在文件中，相关 Agent 读取后再继续工作。

Evaluator 的判断以应用的实际运行结果为依据。以全栈应用为例，它会使用 Playwright 操作正在运行的应用，检查 UI、API 和数据库状态，再从产品深度、功能完整度、视觉设计和代码质量四个方面进行评价。只要有一项得分低于规定阈值，本轮评估就不通过。

不过，独立的 Evaluator 仍然需要校准。在早期测试中，它有时已经发现实际问题，却又认为问题并不严重，最终仍判定实现通过；它也容易停留在表面测试，没有继续检查边界情况。经过多轮提示词调整后，Evaluator 仍可能遗漏布局、交互和深层功能中的问题。

Anthropic 以构建一款 2D 复古游戏制作器为案例，对比了 Claude Opus 4.5 在单 Agent 和完整 Harness 两种方案下的表现。

方案运行时间成本规划方式实际结果
单 Agent约二十分钟九美元直接处理简短需求生成了编辑器和试玩界面，但核心游戏无法响应输入
完整 Harness约六小时约两百美元Planner 将需求扩展为包含 16 项功能、分布在 10 个 Sprint 中的产品规格Evaluator 在构建过程中发现了矩形填充、实体删除和 FastAPI 路由顺序等具体缺陷。
最终角色能够移动，核心游戏可以实际试玩，但仍存在角色与平台重叠、关卡无法通过等问题。

这组结果只反映该案例中的表现，不能视为 Harness 在不同任务和模型上的普遍收益。

备注： Opus 4.6 能够持续执行更长时间的 Agent 任务，长上下文检索能力也有所提升。因此，更新后的 Harness 移除了 Sprint，让 Generator 连续完成整个构建过程，再由 Evaluator 在构建结束后集中评价。

当任务已经处于当前模型能够独立、可靠完成的范围内时，Evaluator 只会增加额外开销；当任务仍接近模型能力边界时，它才更可能带来明显收益。

因此，是否拆分实现轮次、是否引入 Evaluator，都应依据当前模型独立完成具体任务的能力来决定。

3. 工程约束与持续维护 ​

用户 Harness 不是配置一次就可以长期不变。Agent 会沿用仓库中已有的模式，其中也包括不理想的模式；随着模型能力提升，原本用于弥补能力缺口的 Harness 组件也可能失去必要性。因此，工程环境、项目约束和 Harness 本身都需要持续调整。

补齐 Agent 所需能力 ​

当 Agent 无法推进高层目标时，问题不一定出在模型本身，也可能是项目缺少必要的工具、抽象和内部结构。此时，可以先把大目标拆解为设计、实现、审查和测试等基础环节，让 Agent 逐步补齐完成这些环节所需的能力，再借助它们处理更复杂的任务。

固化工程约束 ​

对于项目中反复出现的问题，仅靠人工逐次修复，无法阻止不良模式继续扩散。可以通过自定义 Lint 规则和结构测试，对架构边界、数据解析方式、结构化日志、类型命名和文件大小等作出约束，并在错误信息中直接给出修复提示。这些规则用于守住系统的不变量，而不限定具体的实现方式，因此 Agent 在边界内仍可自行选择方案。

对于逐渐积累的架构漂移和技术债，还可以将重要的工程偏好编码为“黄金原则”，再通过周期性后台任务扫描偏差、更新质量评分，并提交针对性的重构 PR。评审意见、重构结果和用户反馈也可以沉淀到文档或工具中，让一次性的人工判断转化为后续 Agent 可以持续复用的环境规则。

调整 Harness 组件 ​

Harness 本身也需要定期检查。调校 Evaluator 时，可以查看它的运行记录，找出评估结果与人工判断不一致的地方，再相应调整评价提示词。模型升级后，则可以逐项移除 Harness 组件，观察最终效果是否下降。如果移除后效果没有变化，就可以在不影响结果的前提下，降低编排复杂度、缩短运行时间并减少 Token 成本。

因此，Harness Engineering 不只是不断增加机制，还要根据实际失败和模型能力，及时修改或移除不再必要的机制。

三、结论 ​

这些实践没有给出一份固定的用户 Harness 组件清单，但它们呈现出相同的工程方向：

  • 将项目知识、任务目标和工作进度保存在 Agent 能够发现的环境中；
  • 将模糊需求转化为明确的范围和完成条件，并在必要时拆分为可以逐步推进的任务；
  • 通过 Guides 在行动前提供引导，通过 Sensors 在行动后发现偏差并推动修正；
  • 将反复出现的问题沉淀为文档、工具和自动检查；
  • 根据实际失败、运行成本和模型能力，持续调整或移除相关机制。

模型为 Agent 提供基础能力，用户 Harness 则影响这些能力能否在具体项目中可靠发挥。因此，Harness Engineering 不是一次性的配置，也不是组件越多越好。判断是否保留一项机制，归根结底需要回答两个问题：

  • 它正在防止哪一种真实发生的失败？
  • 它带来的可靠性收益是否值得相应的成本、延迟和维护复杂度？
