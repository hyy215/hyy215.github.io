理解 Loop Engineering：从逐步提示 Coding Agent 到设计可收敛的反馈循环 ​

使用 Coding Agent 时，人通常负责推动整个过程：提出任务，等待结果，查看测试结果，再决定是补充信息、要求修改，还是结束任务。

当 Agent 已经能够读取项目、修改代码和运行测试后，一个自然的问题随之出现：这些重复的推动工作，是否也可以交给系统？系统能否保存目标，读取每轮结果，自动发起下一轮，并在完成或无法继续时停止？

这就是 Loop Engineering 试图讨论的问题。它的重点不是让 Agent 无限制运行，而是把原来由人决定的“继续、调整还是停止”，交给一套能根据反馈自行运转的机制。

一、Loop Engineering 从哪里来 ​

The Pragmatic Engineer 对这段传播过程的追查从 Geoffrey Huntley 的 Ralph Wiggum 方法讲起。Ralph Loop 的核心做法是先定义目标和成功条件，把工作拆成计划；每轮只处理其中一项，完成后检查总体目标，未达成就用新的上下文启动下一轮。

随后，Claude Code 负责人 Boris Cherny 表示，自己的工作已经从直接提示 Claude，转向设计一套能向 Claude 发出指令并决定后续动作的循环。Peter Steinberger 也提出，与其继续逐步提示 Coding Agent，不如设计能够提示它们的循环。2026 年 6 月，Addy Osmani 在文章 《Loop Engineering》中集中解释了这种工作方式：人不再亲自输入每一步，而是设计一个能够发现工作、分配任务、检查结果、记录进展并决定下一步的系统。

结合这些实践，可以把 Loop Engineering 概括为：

为 Coding Agent 设计一套持续执行机制：系统保存目标和状态，让每轮结果影响下一步行动，并在达到完成条件、资源上限或需要人工介入时停止。

图 1：Loop Engineering 根据每轮执行结果持续反馈，并在验证后决定迭代或停止。

二、一个成熟的 Loop 通常需要哪些能力 ​

Addy Osmani 在《Loop Engineering》中把当前产品中的 Loop 能力概括为五项：自动化、Worktree、Skill、插件与连接器、子 Agent。此外，还需要在对话之外保存任务状态。这些能力并非每种 Loop 都必须具备，而是分别解决触发、隔离、知识复用、工具连接和任务拆分等问题。

图 2：五类能力各自解决不同问题，持久状态负责在多轮执行之间保存必要信息。

自动化：负责触发任务 ​

自动化决定循环何时启动。它可以定时运行，也可以由 CI 失败、新 Issue、生产告警或用户反馈触发。

自动触发本身还不构成 Loop：如果系统每次都忽略上次结果，只重复同一条提示词，它仍然只是定时任务。

持久状态：让下一轮知道发生过什么 ​

长期任务不能只依赖不断增长的聊天记录。

计划、已完成事项、失败尝试、当前阻塞和下一步工作，需要保存在仓库文件、任务系统或其他外部载体中。这样，Agent 可以在新的上下文中读取已有进度，继续推进任务。

外部状态也不等于完整保存所有历史。只有会改变下一轮判断的信息才值得留下；过期计划和互相矛盾的日志反而会造成目标漂移。

Worktree：隔离并行任务的修改 ​

当多个 Agent 同时处理同一仓库时，Worktree 可以为每个 Agent 创建独立的工作目录，避免彼此覆盖文件。

它解决的是并行执行时的文件冲突，不是所有 Loop 的必备条件。单线程循环不一定需要 Worktree，代码合并和人工评审仍然可能成为瓶颈。

Skill：沉淀可复用的项目知识 ​

构建命令、目录约定、验收方式和历史决策如果只存在于某次对话里，下一轮就需要重新猜测。

Skill 把这些可复用知识保存为 Agent 每次运行都能读取的说明，使循环不必反复从零理解项目。

插件与连接器：连接实际使用的工具 ​

仅能读写本地文件的循环作用有限。

连接器让 Agent 读取 Issue、CI、错误监控或消息系统，也让它能够创建 PR、更新任务和通知工程师。

接入范围越广，权限控制和人工审批越重要，尤其不能把生产变更等不可逆操作完全交给自动循环。

子 Agent：把执行与检查分开 ​

让生成代码的 Agent 同时负责验收，容易延续自身的错误判断。更稳妥的做法是优先使用结果明确的自动化测试；只有在需要判断语义或设计是否合理时，才引入使用独立指令的检查 Agent。但需要注意的是，检查 Agent 会增加成本，只有能够提供新证据时才值得使用。

无论验证由自动化测试还是检查 Agent 完成，结果都要成为下一轮的判断依据。系统根据这些证据决定继续执行、确认完成或提前停止。因此，在启动 Loop 之前，需要写清目标、完成证据和退出条件。

当预先约定的测试全部通过，或经明确规则确认没有待办时，循环可以正常结束；缺少权限、连续没有进展、达到预算上限或需要人工判断，则意味着循环应当停止，并把问题交还给人。

三、Codex 和 Claude Code 中的 /goal 与 /loop ​

Codex：用 /goal 持续推进目标 ​

Codex 的 Goals 文档将 Goal 定义为一种持久目标，适合终点明确、但实现路径需要经过多轮探索的任务。它把目标和完成条件保存在当前线程中，让 Codex 持续检查进展，直到目标完成、达到限制或需要用户介入。

用户可以直接输入 /goal 设置目标，也可以在输入区域选择 Goal 模式，再写下希望持续推进的结果。

图 3：在 Codex 中为当前任务启用 Goal。截图自：OpenAI，《Using Goals in Codex》，访问于 2026-08-04。OpenAI Cookbook，Copyright © 2025 OpenAI，MIT License。

启用 Goal 后，Codex 会在一轮工作结束时检查证据：目标已经满足则完成；目标尚未满足且允许继续时，则进入下一轮。

图 4：普通提示词与 Codex Goal 的执行方式对比。来源：OpenAI，《Using Goals in Codex》，原文 Figure 1。OpenAI Cookbook，Copyright © 2025 OpenAI，MIT License。

例如，/goal 可以要求系统把结账服务的 p95 延迟降到 120 ms 以下，同时保持正确性测试通过。这里真正驱动循环的不是“继续优化”这句话，而是性能指标、正确性约束和可重复运行的基准测试共同组成的完成条件。

图 5：明确的结果、验证方式和约束共同构成可检查的 Goal。来源：OpenAI，《Using Goals in Codex》，原文 Figure 4。OpenAI Cookbook，Copyright © 2025 OpenAI，MIT License。

Goal 是保存在当前线程中的持久状态，记录目标、生命周期、预算和用量。它不属于全局记忆，也不是项目级指令。

图 6：Goal 在线程中保存目标、状态、预算和用量，并连接证据检查、后续轮次与生命周期控制。来源：OpenAI，《Using Goals in Codex》，原文 Figure 2。OpenAI Cookbook，Copyright © 2025 OpenAI，MIT License。

一轮工作结束后，Codex 会检查是否可以继续。只有目标尚未完成、Goal 仍处于活动状态、线程已经空闲、没有等待处理的用户输入、预算仍然允许，并且不存在需要用户处理的阻塞时，Codex 才会启动下一轮。

用户可以暂停、恢复或清除 Goal。目标通过证据验证后，Goal 会进入完成状态；达到预算上限后，则会进入预算受限状态，不再自动继续。

图 7：Codex Goal 的生命周期和自动继续条件。来源：OpenAI，《Using Goals in Codex》，原文 Figure 3。OpenAI Cookbook，Copyright © 2025 OpenAI，MIT License。

Claude Code：区分周期执行与条件执行 ​

Claude Code 同时提供 /loop 和 /goal。

/loop 可以按照固定的时间间隔重复执行提示词，也可以让 Claude 自行决定下一次执行时间。它还能定期调用其他命令，适合“每隔五分钟检查一次部署”这类需要等待外部状态变化的任务。

/goal 不按时间间隔触发。每轮结束后，一个独立的小模型会根据会话记录检查完成条件；如果条件尚未满足，Claude 就会开始下一轮。这个检查模型不会自行读取文件或运行命令，因此 Claude 需要在会话中明确给出测试结果等依据。对于可能无法完成的任务，官方文档也建议设置时间或轮次上限。

两种机制解决的问题不同：/loop 适合等待外部状态并周期检查，/goal 适合在一个可验证目标上连续推进。在更大的自动化流程中，可以先由定时任务发现新的失败，再针对某个失败持续修复，直到测试通过。

四、公开分享案例：让 Agent 接管夜间端到端测试 ​

The Pragmatic Engineer 记录了工程经理 Utku K 公开分享的一套夜间端到端测试流程。

前端应用每晚按计划运行 E2E 测试。测试失败后，Agent 不会立即把它当成产品缺陷，而是先判断这是确实存在的回归问题，还是误报。如果确认存在缺陷，Agent 会尝试修改代码并重新运行测试，再根据结果继续调整。测试通过后，循环结束；如果达到重试上限仍未解决，则停止尝试并上报给工程师。最终，Agent 会提交一个等待工程师审查的 PR。

这套流程也对应了前文提到的各项控制要素：

  • 触发条件：夜间 E2E 测试失败；
  • 目标：确认失败原因，并在确有缺陷时修复代码；
  • 行动：调查、修改代码和重新运行测试；
  • 反馈：新的测试结果；
  • 完成条件：测试通过并准备好 PR；
  • 退出条件：达到重试上限后上报；
  • 人工审核：工程师审查 PR，而不是让循环直接决定生产变更。

这个案例之所以能说明 Loop Engineering，不是因为测试会在夜间自动运行，而是因为每轮结果都会决定下一步动作：测试失败后开始诊断，诊断结果决定是否修改代码，复测结果决定继续还是结束，重试上限则防止系统无休止地消耗资源。

五、工具会接管循环，但不会接管责任 ​

Loop Engineering 把工程师从逐轮提示的位置移开，却没有把人从责任链中移除。循环可以根据反馈决定下一步，但目标是否合理、证据是否充分、权限是否合适，以及最终结果能否接受，仍然需要工程师判断。

Addy Osmani提醒，自动循环可能错误地判断任务已经完成，也可能让代码的增长速度超过工程师的理解速度。如果使用者不再复核结果，错误会不断累积，后续的审查、调试和修改也会变得更加困难。

因此，人工介入并不意味着循环失败。当循环无法继续、操作风险过高或需要结合更多背景作出判断时，系统应当停止执行，把已有结果和决定权交还给人。

Loop Engineering 能否长期作为一个独立概念存在，目前仍不确定。The Pragmatic Engineer转述了杰出工程师 Max Kanat-Alexander 的判断：随着 /goal 等能力逐渐进入 Coding Agent 产品，手写 Loop 可能只是过渡方案。但即使工具接管了多轮执行，工程师仍然需要设计目标、验证方式、停止条件和人工介入的边界。
