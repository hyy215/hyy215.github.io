ui-forge 过程与审批 ​

任务执行时，用户既要看到 Codex 在做什么，也要在需要时回答问题、确认操作。这两件事使用同一条通信链路，但处理方式不同：过程消息用来展示，审批和提问需要校验后回复。

执行过程如何展示 ​

Codex 会持续发送消息、命令输出和文件修改等进度。ui-forge 根据事件中的会话、轮次和执行项标识，找到需要更新的内容。源码：事件路由与展示更新

委派子任务子任务信息及执行状态

审批请求如何往返 ​

以命令审批为例：

  1. Codex 发出 item/commandExecution/requestApproval，带上原生请求 ID 和待确认的操作。
  2. codex-client 保存请求，生成随机 token，Server 把它发送给所属任务的页面或 CLI。
  3. 用户选择决议，客户端提交任务 ID、token 和结果；如果是提问或表单，则提交填写的内容。源码：交互面板
  4. 后端校验通过后，用原始 request.id 将结果回传给 Codex，由 Codex 处理后续执行。

ui-forge 负责传递用户决议，不会自行批准请求，也不在用户点“允许”后代替 Codex 执行命令。源码：请求回复

token 解决什么问题 ​

Codex 原生 request.id 只在当前连接内有效，新连接可能再次使用相同 ID。随机 token 将用户回复绑定到这一次请求，避免旧页面的回复误匹配新连接里的请求。

token 是这次待回复请求的标识，不是账号登录凭据。后端校验的重点是：

  1. token 还在当前连接的待回复表里。
  2. 请求属于当前任务，子线程也必须能追溯到主任务。
  3. 用户提交的结果符合这个请求对应的 Schema（数据格式约束）。
  4. 同一请求正在提交回复时，拒绝其他入口的重复提交；发送成功后移除请求，并通知各入口更新状态。

这些检查依据当前连接中的真实请求，不依据页面上的按钮或展示缓存。源码：请求校验

断线后，哪些审批还能处理 ​

场景重新打开时怎么处理
只关闭页面，Server 和 Codex 连接仍在从当前连接的 pendingRequests() 读取属于这个任务的待回复请求，放入重连快照
请求已由 CLI 处理，或已被 Codex 撤销不再放入重连快照，旧页面提交的回复也会被拒绝
Server 或 Codex 进程已关闭待回复表与 token 清空，历史记录不能用于重放授权

所以，重连时恢复的是当前仍有效的请求，不是照搬历史审批卡片。源码：订阅时读取待回复请求

审批有哪些权限边界 ​

VS Code 插件只允许在任务对应的项目中继续、停止或处理审批，并要求工作区已受信任。创建任务时，目标目录以当前工作区为准，不接受页面传入的其他目录。CLI 不经过这些插件检查，但仍受 Codex 的沙箱和审批策略限制。源码：工作区检查
