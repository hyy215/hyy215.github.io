ui-forge 会话恢复与状态一致性 ​

ui-forge 支持在页面和 CLI 中操作同一个任务。这里要解决的是：用户关掉页面后，任务还能不能运行？服务重启后，历史从哪里找回来？两个入口同时操作，会不会重复执行？

任务如何建立和保存 ​

先区分两个概念：thread 是一整个会话，turn 是会话中的一轮执行。用户第一次提交需求会启动一轮，后续修改可以在同一个会话中继续。

本地服务（下文称 Server）准备好运行环境后，按顺序完成三件事：

  1. 调用 thread/start 创建会话，把返回的 thread.id 作为 ui-forge 的 taskId。
  2. 保存任务索引，将这个 ID 与目标项目、设计绑定关联起来。
  3. 调用 turn/start，传入需求和图片，开始第一轮执行。

会话创建后，Server 才会启动第一轮执行。如果这一步报错，已创建的任务仍会保留。用户可以打开原任务查看状态，再决定是否继续，不必重新创建任务。源码：创建与首轮启动

创建任务后，数据分成三类：完整历史交给 Codex，导航和辅助信息由 ui-forge 落盘，当前连接的展示状态放在内存里。

数据保存位置作用
用户输入、模型回复、轮次和工具历史Codex 原生会话存储恢复对话和读取执行历史
任务 ID、项目目录、标题、更新时间、设计绑定sessions.json展示列表，定位原会话
规则指纹、运行配置、Agent 摘要、已观测的 Tokendiagnostics/排查问题，不驱动执行
用户上传的图片attachments/向 Codex 提供本地图片文件
展示缓存、已装载标记、待回复审批Server 内存支持当前连接和客户端重连

ui-forge 的文件默认位于安装目录的 .ui-forge/runtime/，可通过 UI_FORGE_RUNTIME_DIR 修改。Codex 原生历史由它自己管理，项目通过接口读取，不直接解析底层文件。

其中，sessions.json 只是任务目录，不是聊天记录备份。只有索引、没有 Codex 原生历史，不能还原对话；索引丢失后，当前列表也不会自动导入其他 Codex 会话。

同时保存多个任务，怎样避免记录丢失

sessions.json 保存的是完整任务列表。每次新增或更新任务，Server 都会生成一份新列表并整体替换文件，而不是在文件末尾追加一条记录。

例如，用户在页面创建任务 A，同时在 CLI 创建任务 B。如果两次更新都基于同一份旧列表，分别保存“旧列表 + A”和“旧列表 + B”，后一次保存就可能覆盖前一次，导致列表里少了一条任务记录。

Server 用两种方式保护这个文件：

  • 排队保存，避免互相覆盖。 A 保存成功后，B 再基于包含 A 的最新列表更新，因此两条记录都能保留。这里的排队只针对同一个 Server 内的索引更新，不是让任务轮流执行。
  • 先写临时文件，避免破坏原文件。 新列表完整写入临时文件后，再替换正式文件，成功后才更新内存中的列表。如果临时文件写入失败，原文件仍然保留。

读取文件时，如果内容损坏或没有读取权限，Server 会明确报错，不会假装任务列表为空。源码：SessionIndex

断开后如何恢复 ​

页面和 CLI 只是操作入口，Codex 进程由 Server 托管。因此，关闭客户端和重启服务是两种不同的情况：

断开的是什么后台任务重新打开时
只关闭页面或 CLI只要 Server 和对应 Codex 进程还在，就可以继续执行复用连接和已装载的会话，发送当前快照，再接后续事件
Server 也退出了它托管的 Codex 进程关闭，内存状态丢失先读取索引恢复任务列表，打开某个任务时再准备连接，通过 thread/resume 加载历史

thread/resume 只是把已有会话装载到当前连接，不会重放旧输入，也不会自动启动新一轮。它不是让旧进程从中断位置继续跑。任务已经装载时则直接复用，不必再次调用。源码：SessionService.load

历史和实时消息怎么接起来 ​

重连的客户端先拿到一份“快照”，也就是当前已有的消息和状态，再持续接收之后发生的“增量”。服务重启时，展示缓存先由 Codex 返回的历史重建。

这里不能先发快照、再开始监听，否则中间的新消息可能漏掉。Server 会先注册监听，再同步复制快照并开启事件队列：此前的事件归入快照，此后的事件进入队列，随后按顺序发送给客户端。消息按轮次 ID 归并，迟到的启动消息也不会把已结束的轮次改回运行中。

快照读取与事件订阅的区别

快照读取接口通过 thread/read 获取原生历史；事件订阅则发送 Server 的展示缓存快照和后续增量。展示缓存用于还原界面，不用于判断能否执行或审批是否有效。具体见 SessionEventHub。

恢复后如何继续或停止 ​

用户发送需求或点击“继续”时，Server 会先读取 Codex 的当前状态，再决定怎样处理：

用户操作当前有轮次在运行当前没有轮次在运行
发送普通消息，例如“把按钮改成蓝色”turn/steer，补进当前轮次turn/start，在原会话中启动新一轮
点击“继续任务”或执行 CLI 的 resume跳过，任务已经在运行turn/start，在原会话中启动新一轮

用户不需要手动选择“补充”还是“新一轮”，两种调用都沿用原会话。手动发送“继续”两个字仍属于普通消息，不等同于“继续任务”操作。

因此，CLI 的 ui-forge resume 不只是原生 thread/resume 的同名包装：它连接原任务后，还会在空闲时发送继续请求。

停止操作通过 turn/interrupt 中断指定轮次。Server 会核对 turnId，防止旧页面误停后来开始的新轮次。RPC 超时不代表操作没有发生，后续操作仍需读取真实状态。源码：读取、发送与停止

多个入口如何协同 ​

页面和 CLI 不互相同步，而是共同操作 Server 中的同一个任务。下面以两端都打开任务 T、各发送一条普通消息为例：

图中 A 的消息先被处理，B 的消息到达时这轮还没结束，因此补进当前轮次。如果处理 B 时已经空闲，就按上一节的规则启动新一轮。任务事件会持续广播给两个已订阅的入口，不只在图末发送一次。

Server 按任务 ID 将发送和停止操作排队，每次处理前重新读取 Codex 状态，不直接相信某个入口显示的“空闲”。队列只等一次操作处理完，不等模型整轮执行结束，所以运行中仍能补充需求或停止。源码：send、stop 和 serial

两端同时打开任务时，Server 也会复用正在进行的连接初始化和会话加载，避免重复恢复。一端处理审批后，另一端会收到已处理事件，旧按钮不能重复提交；具体见过程与审批。

如何避免重复恢复

连接初始化和会话加载分别共用进行中的 Promise，后来的请求等待同一次操作。已经装载的会话直接复用，不再重复调用 thread/resume。

这里保证的是共用任务、按真实状态处理操作，再通过事件和重连快照更新展示，不是两个界面每一刻都完全相同。排队也不等于输入去重：两端发送相同文字仍是两次输入，这套机制只处理同一个 Server 内的并发。
