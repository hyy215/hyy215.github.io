JavaScript 事件循环详解：Node.js 篇 ​

Node.js 与 libuv ​

理解 Node.js 事件循环，首先需要澄清“Node.js 是单线程”这一常见说法。默认情况下，用户 JavaScript 以及异步操作完成后触发的 JavaScript 回调，都在同一条事件循环线程上执行。但 Node.js 进程还包含 libuv 线程池中的工作线程，以及 V8 等组件使用的后台线程；应用也可以通过 worker_threads 创建额外的 JavaScript 执行线程。

Node.js 的异步工作并非由单一组件完成，而是由 JavaScript 引擎、Node.js 运行时、libuv 和操作系统协作完成：

层次或组件主要职责
V8编译并执行 JavaScript，管理 JavaScript 堆内存和垃圾回收
Node.js API 与绑定层向 JavaScript 暴露文件系统、网络和计时器等能力，在 JavaScript 与底层原生接口之间转换调用和结果
libuv 事件循环提供跨平台事件循环，接收 I/O 事件和线程池完成通知，并驱动事件循环各阶段
操作系统的 I/O 机制监视网络套接字等资源，在资源就绪或操作完成时通知 libuv
libuv 线程池执行不适合在事件循环线程中直接完成的工作，例如异步文件系统操作、dns.lookup() 以及部分加密和压缩任务

事件循环阶段 ​

本节以 libuv 1.45+ 为行为基线；Node.js 20.3.0 是首个集成 libuv 1.45.0 的 Node.js 版本。在这一实现中，每轮循环内部会在 poll、check 和 close callbacks 之后处理到期计时器；此前版本则在 poll 之前处理。为兼容旧行为，进入第一轮循环迭代前仍会检查一次到期计时器。

在这个基线下，一轮事件循环会依次处理 pending callbacks、idle/prepare、poll、check、close callbacks，然后处理 timers。为便于理解，可以把每个阶段看作负责一类回调。事件循环进入某个阶段后，会依次处理当前可以执行的相应回调；当没有更多回调或达到系统限制时，再进入下一阶段：

  • pending callbacks：执行上一轮循环中被推迟的 I/O 回调，通常是系统层面的错误通知（如 TCP 的 ECONNREFUSED）。
  • idle, prepare：仅 Node.js 内部使用。
  • poll：处理轮询队列中的 I/O 回调，并决定是否阻塞等待新的 I/O 事件。
    • 如果队列不为空，则依次同步执行其中的回调，直到队列清空或达到系统上限。
    • 如果队列为空，但已有 setImmediate() 回调待执行，则不阻塞，直接进入 check 阶段。
    • 如果队列为空且有待触发的计时器，则最多阻塞到最近计时器到期；如果在此之前有新的 I/O 事件到来，就转而处理相应回调。
    • 如果队列为空，既没有 setImmediate()，也没有待触发的计时器，但仍有活跃的 I/O handle 或 request，则可以持续等待新的 I/O 事件。
    • 如果已经没有活跃的 handle 或 request，事件循环便可以结束，而不会继续等待。
  • check：执行 setImmediate() 回调函数。
  • close callbacks：执行关闭类回调，如 socket.on('close', ...)。
  • timers：执行已到期的 setTimeout() 和 setInterval() 回调。计时器的阈值是最早可执行时间，而非精确执行时间；操作系统调度和其他回调的执行都可能使它延迟。

计时器阈值与回调延迟 ​

计时器设置的是最早可执行阈值，而非精确执行时间。假设文件读取在 95ms 后完成，其回调耗时 10ms：事件循环在 poll 阶段执行文件读取回调，等它结束时已经过去约 105ms。此时 100ms 计时器虽然已经到期，但仍需等待当前 poll 阶段结束，待事件循环进入 timers 阶段后才能执行。

因此，在这个假设下，计时器回调最早会在约 105ms 后执行；实际时间还可能因文件系统、操作系统调度和其他回调进一步延迟。

以下示例改编自 Node.js contributors，The Node.js Event Loop：timers。

js
const fs = require('node:fs');

function someAsyncOperation(callback) {
  // 概念假设：文件读取在约 95ms 后完成
  fs.readFile('/path/to/file', callback);
}

const timeoutScheduled = Date.now();

setTimeout(() => {
  const delay = Date.now() - timeoutScheduled;

  console.log(`${delay}ms have passed since I was scheduled`);
}, 100);

someAsyncOperation(() => {
  const startCallback = Date.now();

  // 模拟耗时 10ms 的回调
  while (Date.now() - startCallback < 10) {
    // 阻塞事件循环
  }
});

setImmediate() 与 setTimeout(0) ​

setTimeout(0) 并不表示立即执行：Node.js 会将小于 1ms 或省略的延迟调整为 1ms，回调仍需等待 timers 阶段。

以下两个示例改编自 Node.js contributors，The Node.js Event Loop：setImmediate() vs setTimeout()。

在 CommonJS 主模块中调用 ​

在 CommonJS 主模块的顶层代码中同时注册两者时，执行顺序不确定：如果进入事件循环前 setTimeout(0) 对应的 1ms 阈值已经到达，计时器回调可能先执行；否则，setImmediate() 会在 check 阶段先执行。

js
// timeout-vs-immediate.cjs
setTimeout(() => {
  console.log('timeout');
}, 0);

setImmediate(() => {
  console.log('immediate');
});

在 I/O 回调中调用 ​

在 poll 阶段执行的同一个 I/O 回调中，同时注册两者时，setImmediate() 会先执行。原因是事件循环离开 poll 后会先进入 check，随后才经过 close callbacks 到达 timers。

js
// timeout-vs-immediate.cjs
const fs = require('node:fs');

fs.readFile(__filename, () => {
  setTimeout(() => {
    console.log('timeout');
  }, 0);
  setImmediate(() => {
    console.log('immediate');
  });
});

next tick 队列与微任务队列 ​

Node.js 中需要区分两套队列：

  • next tick 队列：保存 process.nextTick() 注册的回调，由 Node.js 维护。
  • 微任务队列：保存已兑现 Promise 的 then、catch、finally 回调，以及 queueMicrotask() 注册的回调，由 V8 管理。

每个回调执行后的队列处理 ​

process.nextTick() 不是事件循环的一个阶段，它只是把回调加入 next tick 队列。

一个事件循环阶段中可能需要执行多个回调。Node.js 每执行完一个计时器、I/O 等 JavaScript 回调，都会先处理 next tick 队列，再处理微任务队列，然后才执行同一阶段的下一个回调或继续事件循环。

何时使用 queueMicrotask() 与 process.nextTick() ​

queueMicrotask() 是 process.nextTick() 的一种替代方案。它不使用 next tick 队列，而是把回调加入微任务队列。

以下示例来自 Node.js contributors，When to use queueMicrotask() vs. process.nextTick()，用于说明两套队列在 ES Module 和 CommonJS 中的执行顺序。

ES Module：

js
import { nextTick } from 'node:process';

Promise.resolve().then(() => console.log('resolve'));
queueMicrotask(() => console.log('microtask'));
nextTick(() => console.log('nextTick'));

// 输出：
// resolve
// microtask
// nextTick

在 CommonJS 中，Node.js 先清空 next tick 队列，再清空微任务队列，因此 nextTick 最先输出。ES Module 本身已经作为微任务的一部分执行，Node.js 会继续处理当前微任务队列中的 Promise 和 queueMicrotask() 回调，然后才处理 next tick 队列。

对于大多数用户代码，Node.js 官方建议使用浏览器和 Node.js 都支持的 queueMicrotask()。在简单场景中，它可以直接替代 process.nextTick()。从 Node.js 20.18.0 和 22.7.0 开始，process.nextTick() 已被标记为 Legacy。

递归调用的风险 ​

无论使用哪一种队列，都不应无限递归注册回调。持续产生 next tick 回调或微任务都可能使计时器和 I/O 长时间得不到处理。

总结 ​

理解 Node.js 事件循环，可以抓住一条主线：当前 JavaScript 回调执行结束后，Node.js 会先处理 next tick 队列和微任务队列，再继续执行同一阶段中的其他回调或推进到后续阶段。libuv 负责驱动计时器、I/O、setImmediate() 和关闭回调等工作，但最终运行的 JavaScript 回调仍会占用事件循环线程。

异步 API 能让事件循环线程不必停下来等待 I/O，却不能消除回调本身的执行成本。耗时的同步代码、过长的回调，以及不断递归产生的 next tick 回调或微任务，都会推迟其他计时器和 I/O。
