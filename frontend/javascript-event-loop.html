JavaScript 事件循环详解：浏览器篇 ​

Event Loop 是浏览器协调 JavaScript 执行、异步事件与页面渲染的核心调度机制。在同一个 JavaScript 执行线程中，同一时刻只会执行一项 JavaScript 工作；浏览器可以借助自身组件、其他线程或操作系统处理 I/O、计时等工作，并在工作就绪后安排相应的任务或回调，等待 JavaScript 主线程执行。本文将梳理浏览器事件循环中的任务、微任务和渲染时机，并通过计时器、动画与事件派发案例说明它们如何共同影响页面响应性。

为什么需要事件循环 ​

单线程与调用栈 ​

在普通的同步函数调用中，调用栈遵循后进先出原则。调用函数时会将相应的执行上下文压入调用栈，并将它作为当前运行的执行上下文；函数调用结束时，该执行上下文会从栈顶弹出，调用方随后继续执行。

以下示例参考 Philip Roberts 在 JSConf EU 2014 的演讲 What the heck is the event loop anyway?：

js
function multiply(a, b) {
    return a * b;
}

function square(n) {
    return multiply(n, n);
}

function printSquare(n) {
    var squared = square(n);
    console.log(squared);
}

printSquare(4);

同步阻塞 ​

当前任务中的 JavaScript 会持续执行，直到这段同步调用链结束。在此期间，如果主线程正在执行耗时操作，事件循环便无法调度其他任务，浏览器通常也无法及时处理用户输入和页面更新，这种情况称为阻塞。

下面使用 Philip Roberts 在 JSConf EU 2014 的演讲 What the heck is the event loop anyway? 中设计的一段伪代码说明同步阻塞。假设 getSync() 会发起同步网络请求，并一直阻塞到请求完成。这些请求会依次阻塞主线程；任一请求迟迟未返回，后续代码、用户交互和页面更新都会被推迟，页面可能出现卡顿甚至“假死”。

js
// 伪代码：getSync() 会阻塞，直到请求完成
var foo = getSync("//foo.com");
var baz = getSync("//baz.com");
var qux = getSync("//qux.com");

console.log(foo);
console.log(baz);
console.log(qux);

浏览器事件循环 ​

浏览器中的主线程与异步工作 ​

上一节的同步请求会让 JavaScript 主线程停下来等待，导致后续代码、用户交互和页面更新都被阻塞。为了避免把主线程耗费在等待上，浏览器提供的大多数网络请求和计时器 API 都采用异步方式：JavaScript 发起操作后便继续执行当前任务中的后续代码；网络 I/O、计时等异步操作由浏览器的其他组件或操作系统处理。

当计时器到期、网络数据到达或用户产生输入时，相应的回调或事件处理函数不会立即打断正在执行的 JavaScript，而是等待事件循环调度。要理解这些工作何时执行以及它们之间的先后顺序，首先需要了解任务和微任务。

任务与微任务 ​

任务与任务队列 ​

任务（task）是事件循环的一次调度单位。任务承载的工作可以是执行页面脚本、调用已经到期的 setTimeout 回调，或者处理真实用户的点击。

每个任务都有对应的任务源（task source），用于表示任务所属的类别。在同一个事件循环中，每个任务源都会关联到一个任务队列，多个任务源也可以共用同一个队列。任务被加入相应的队列后，其中可运行的任务等待事件循环选择并执行。

微任务与微任务队列 ​

微任务（microtask）是另一类待执行工作，通常会在事件循环选择下一个任务之前处理。Promise 进入 fulfilled 或 rejected 状态后需要执行的 then、catch 和 finally 回调、MutationObserver 回调，以及通过 queueMicrotask() 注册的回调，都会作为微任务加入微任务队列。

当前任务结束后，事件循环会执行微任务检查点，依次处理队列中的微任务。如果处理过程中又产生了新的微任务，它们也会在本次检查点中继续执行，直到微任务队列为空。

浏览器事件循环的运行流程 ​

HTML 规范定义了不同的任务源，例如计时器、用户交互、网络、DOM 操作、导航与历史遍历、页面渲染等，但没有规定浏览器必须设置多少个任务队列，也没有规定哪些任务源应该共用一个队列。

每轮循环中，浏览器会从包含可运行任务的队列中选择一个队列，并执行其中最早的可运行任务。具体选择策略由浏览器实现；例如，浏览器可以提高用户交互任务的优先级，以便更快响应输入。无论采用何种策略，同一任务源中的任务都会保持原有顺序。

事件循环每轮处理任务时，可以简化为以下过程：

  1. 从包含可运行任务的队列中选择一个队列；
  2. 取出该队列中最早的可运行任务，并执行它的步骤。如果任务调用了 JavaScript，则同步调用链会持续执行到结束；
  3. 执行微任务检查点，依次处理微任务队列中的所有微任务；
  4. 进入下一轮循环并重新选择任务。

页面渲染如何参与事件循环 ​

页面渲染也由上述事件循环调度，但它不是每轮循环中固定执行的一个步骤。按照当前的 HTML 规范，窗口事件循环会并行等待渲染机会。

“渲染机会”是指浏览器根据屏幕刷新率、页面可见性和限流策略等因素，判断当前可以呈现下一帧的时机。

出现渲染机会后，浏览器会通过渲染任务源排入一个更新渲染的任务。这个任务与其他任务一样，需要等待事件循环选择。被选中后，浏览器会执行 requestAnimationFrame 回调，并根据页面变化按需完成样式计算、布局和绘制等更新。因此，前面的任务或微任务长时间占用主线程时，页面更新也会被推迟。

页面不可见时，浏览器会跳过这次渲染更新。即使页面可见，如果更新不会产生可见变化，并且没有待执行的 requestAnimationFrame 回调，浏览器也可以省略这次更新。此外，浏览器还可能出于调度或性能限流等原因推迟渲染。

以 Chromium 为例，页面 JavaScript、样式计算、布局和绘制记录的生成主要由渲染进程的主线程完成。因此，耗时的 JavaScript 会推迟这些工作和页面更新。虽然栅格化和图层合成可以交由其他线程或进程处理，但页面发生变化时，通常仍要先等待主线程生成所需的结果。具体实现可参考 RenderingNG 架构。

从开发者角度看，可以将页面渲染过程简化为以下几个阶段。一次页面更新不一定会经过所有阶段：

  • Style：计算元素的最终样式
  • Layout：计算元素的尺寸和位置
  • Paint：生成描述绘制内容和顺序的记录
  • Raster：将绘制记录转换为像素
  • Composite：组合各图层并生成最终画面

setTimeout 为什么不一定准时执行 ​

setTimeout() 的延迟参数表示回调最早可以执行的时间，而不是回调一定会执行的时间。

js
console.log('hi');

setTimeout(function cb() {
  console.log('cb');
}, 1000);

console.log('over');

  2. 调用 setTimeout() 注册计时器，JavaScript 随即继续执行后面的代码并输出 over；
  3. 等待至少 1000 ms 后，回调对应的任务才有机会进入队列；
  4. 该任务不能打断正在执行的任务，需要等待当前同步代码结束并完成随后的微任务检查点；
  5. 事件循环选中该任务后执行回调，输出 cb。

页面更新与动画 ​

页面样式何时更新 ​

修改 DOM 或 CSS 不会立即把新画面显示到屏幕上。当前任务中的同步代码会先执行完，浏览器再在后续的渲染机会中根据页面的最终状态更新画面。因此，同一个任务中的连续样式修改通常会合并到同一次渲染。

连续样式修改为什么不会分别显示 ​

下面两次样式修改发生在同一个任务中，都会立即更新元素的内联样式，但当前 JavaScript 任务尚未结束，浏览器通常不会在两次修改之间更新画面。等浏览器获得渲染机会时，display 已经恢复为 none，因此页面通常不会显示中间的 block 状态。

js
document.getElementById("div").style.display = "block";
document.getElementById("div").style.display = "none";

使用 requestAnimationFrame 分隔更新 ​

requestAnimationFrame() 会请求浏览器在后续一次渲染更新中执行回调。回调不进入普通任务队列，而是由浏览器的渲染流程统一调度，并在样式计算和布局之前执行。

只调用一次 requestAnimationFrame，不能保证在回调执行前，第一次 transform 修改已经显示在页面上。浏览器会在下一次渲染更新中先执行回调，随后才计算样式和布局。因此，两次 transform 修改可能在同一次样式计算前完成，浏览器最终只会用第二个值更新画面，过渡效果也就可能不会启动。

js
const box = document.querySelector('.box')

box.style.transform = 'translateX(1000px)'
requestAnimationFrame(() => {
  box.style.transition = 'transform 1s ease'
  box.style.transform = 'translateX(500px)'
})

可以在 requestAnimationFrame 回调中再注册一次回调。内层回调不会在当前这次渲染更新中执行，而要等待后续的渲染机会。这样两次修改通常会在不同的渲染更新中处理，使第一次设置的 transform 有机会成为过渡的起始状态；但浏览器仍可能因为限流或丢帧而推迟画面呈现。

js
box.style.transform = 'translateX(1000px)'
requestAnimationFrame(() => {  // 下一次渲染更新
  requestAnimationFrame(() => {  // 后续的渲染更新
    box.style.transition = 'transform 1s ease'
    box.style.transform = 'translateX(500px)'
  })
})

这一步只会立即计算样式，不会马上更新屏幕；读取某些属性时，还可能需要重新计算布局。频繁强制计算样式会增加主线程负担。因此，更建议使用双层 requestAnimationFrame 配合 CSS Transition 来分隔两次样式修改；对于更复杂的动画，可以使用 CSS Animation 或 Web Animations API。

requestAnimationFrame 与连续动画 ​

每次调用 requestAnimationFrame() 只会注册一次回调；如果需要连续动画，必须在回调中再次调用。

下面用两个简化的动画循环对比 requestAnimationFrame() 和 setTimeout()：

js
// 方法 1：在页面渲染前移动一次
function rafCallback() {
  moveBoxForwardOnePixel();
  requestAnimationFrame(rafCallback);
}
requestAnimationFrame(rafCallback);

// 方法 2：每次计时器回调移动一次
function timerCallback() {
  moveBoxForwardOnePixel();
  setTimeout(timerCallback, 0);
}
setTimeout(timerCallback, 0);

进阶案例：事件派发与微任务检查点 ​

用户点击事件与 JavaScript 的 click() 方法 ​

同一个 click 事件，通过真实用户操作触发和通过 JavaScript 的 click() 方法触发，微任务的执行时机可能不同。先看下面的例子：

js
const button = document.querySelector('#button');

button.addEventListener('click', function CB1() {
  console.log('Listener 1');
  setTimeout(() => console.log('Timeout 1'));
  Promise.resolve().then(() => console.log('Promise 1'));
});

button.addEventListener('click', function CB2() {
  console.log('Listener 2');
  setTimeout(() => console.log('Timeout 2'));
  Promise.resolve().then(() => console.log('Promise 2'));
});

真实用户点击 ​

真实用户点击由浏览器发起。第一个事件监听器执行完毕后，如果 JavaScript 调用栈已经清空，浏览器会执行微任务检查点，因此先输出 Promise 1，再继续调用第二个监听器。同理，第二个监听器结束后会先输出 Promise 2。两个 setTimeout() 回调属于后续任务，最后依次执行。

图 5：真实鼠标点击作为独立任务触发两个 click 监听器；每个监听器返回且 JavaScript 调用栈清空后，浏览器会执行微任务检查点。

JavaScript 调用 click() ​

调用 button.click() 时，浏览器会在当前 JavaScript 调用过程中同步派发 click 事件。两个监听器执行期间，外层调用栈还没有清空，因此它们产生的微任务暂时不会执行。等 button.click() 返回、调用栈清空后，浏览器才依次处理 Promise 1 和 Promise 2。

图 6：JavaScript 在当前调用栈中调用 click()；两个监听器同步执行完毕后，才处理它们产生的 Promise 微任务。

对自动化测试的影响 ​

如果自动化测试直接调用 DOM 的 element.click()，事件会在当前 JavaScript 调用中同步派发，执行顺序可能与真实用户输入不同。因此，如果测试需要更接近真实用户的输入过程，可以使用 Playwright 等自动化工具模拟鼠标移动、按下和松开。

对默认行为的影响 ​

这种差异还可能影响 preventDefault()。下面的代码先等待一次点击，再在 Promise 回调中阻止链接跳转：

  link.addEventListener('click', resolve, { once: true });

Web Worker 与并行执行 ​

浏览器可以在页面主线程之外处理网络请求、计时器等工作，但这些操作对应的页面回调仍要回到主线程执行。如果回调本身包含大量计算，用户交互和页面渲染依然会被阻塞。Web Worker 的作用，是让一段 JavaScript 在独立于页面主线程的执行环境中运行。

Worker 适合大规模排序、数据解析、压缩和图像处理等 CPU 密集型工作。使用前也要考虑脚本启动和数据传递的成本；如果工作很短，或者主要是在等待网络响应，移入 Worker 不一定更快。

从 Agent 模型理解 Worker ​

MDN 的 JavaScript 执行模型使用 Agent 描述能够独立执行 JavaScript 的主体。页面所在的 Window Agent 与它创建的 Dedicated Worker Agent 各自拥有堆、执行上下文栈和作业队列，可以分别推进事件循环，因此两边的 JavaScript 有机会并行执行。

图 7：HTML 页面与 Worker 分别拥有独立的堆、执行上下文栈和作业队列。改编自：Mozilla Contributors，JavaScript execution model，CC BY-SA 2.5 或更高版本；已将图中文字翻译为中文。

Worker 不能直接访问 window、document 或操作 DOM，但可以使用 JavaScript 内置对象，以及 fetch()、计时器等 Worker 环境支持的 Web API。

创建 Worker ​

下面使用模块脚本创建 Worker。new URL(..., import.meta.url) 让 Worker 文件相对于当前 JavaScript 模块定位，也便于 Vite、webpack 等构建工具识别和处理该文件：

js
// main.js
const worker = new Worker(
  new URL('./task.js', import.meta.url),
  { type: 'module', name: 'sum-worker' }
);

worker.addEventListener('message', event => {
  console.log('计算结果：', event.data.result);
  worker.terminate();
});

worker.addEventListener('error', event => {
  console.error('Worker 执行失败：', event.message);
  worker.terminate();
});

worker.postMessage({ numbers: [1, 2, 3, 4] });

postMessage()不会同步调用另一端的代码，而是把消息任务排入接收方的事件循环；接收方的事件循环执行该任务时，才会触发 message 事件。

消息中的数据如何传递 ​

页面向 Worker 发送数据时，常见的处理方式有三种：

  • 复制一份数据（结构化克隆）：这是默认方式。页面和 Worker 各自得到一份数据，修改其中一份不会影响另一份。
  • 把数据交给 Worker（转移所有权）：适合大型 ArrayBuffer。浏览器不再复制数据，而是把保存数据的那块内存交给 Worker。发送后，页面中的 buffer 变量仍然存在，但已经无法访问原数据，byteLength 也会变为 0。
  • 双方共用数据（共享内存）：页面和 Worker 可以通过 SharedArrayBuffer 操作同一块内存，但同时修改容易产生冲突。这种方式需要满足跨源隔离等安全要求，并使用 Atomics 协调读写，通常不必优先考虑。

下面的示例通过第二个参数 [buffer] 告诉浏览器把这块内存交给 Worker。发送后，页面中的 buffer.byteLength 变为 0：

js
const buffer = new ArrayBuffer(1024);

worker.postMessage({ buffer }, [buffer]);
console.log(buffer.byteLength); // 0

生命周期与使用边界 ​

页面可以调用 worker.terminate() 立即终止 Worker，Worker 也可以调用 close() 停止自身。需要保存结果或释放资源时，应先完成收尾，再结束 Worker。

总结 ​

理解浏览器事件循环，可以抓住一条主线：JavaScript 执行完当前同步代码后，浏览器再安排已经就绪的任务和微任务，并在合适的渲染机会更新页面。

异步机制让 JavaScript 不必同步等待计时器到期、网络响应或用户输入等条件，而是在条件满足后调度相应的任务或微任务。但后续回调仍会占用执行它的 JavaScript 线程。如果回调包含大量计算，主线程依然可能被阻塞，这类工作可以考虑移入 Worker。判断代码是否影响响应性，关键要看后续代码在哪个线程执行、执行多久，以及是否会持续产生新的任务或微任务。
