React Scheduler 原理解读 ​

ReactScheduler调度

scheduler 是一个可以单独安装和引用的独立包，并非只能由 React 内部调用；不过在本文对应的版本中，它主要服务于 React，公共 API 尚未稳定。本文基于 React v19.1.1 对应的 scheduler@0.26.0，先介绍 Scheduler 自身重点涉及的两项机制：

  • 基于优先级的任务调度
  • 协作式时间切片

最后说明 React 如何使用 scheduler。

任务与优先级调度 ​

在 Scheduler 内部，任务（Task） 是任务队列中的调度节点，它封装一个待执行的回调以及该回调的开始时间、过期时间和优先级。

任务结构 ​

本文涉及的 Task 核心字段如下：

  • id：标识符（自增数值）
  • callback：要执行的回调函数；Task 被取消时会被置为 null
  • priorityLevel：任务的优先级
  • startTime：任务可执行的最早时间
  • expirationTime：任务的过期时间，由 startTime 加上对应优先级的超时时长得到；在 startTime 相同的前提下，优先级越高，任务越早过期
  • sortIndex：用于堆排序的字段

任务队列 ​

Scheduler 使用两个队列管理不同状态的任务。它们都通过数组实现为最小堆，并按照各自任务的 sortIndex 排序：

  • taskQueue：存储可以执行的任务，按 expirationTime 排序
  • timerQueue：存储延时任务，按 startTime 排序；任务到期后转移至 taskQueue
ts
var taskQueue: Array<Task> = [];
var timerQueue: Array<Task> = [];

说明：unstable_scheduleCallback 支持通过 options.delay 创建延时 Task；但 React v19.1.1 的生产代码未传入该选项，因此不会使用 timerQueue。下文只讨论 React 实际使用的无延时路径。

最小堆排序 ​

Scheduler 使用最小堆（Min Heap）管理任务，以便频繁找出下一个要处理的 Task。最小堆不要求所有 Task 完全有序，只保证排序最靠前的 Task 位于堆顶。

Task 排序时先比较 sortIndex；当 sortIndex 相同时，再比较 id。比较函数如下：

ts
function compare(a: Node, b: Node) {
  const diff = a.sortIndex - b.sortIndex;
  return diff !== 0 ? diff : a.id - b.id;
}

任务初始化 ​

unstable_scheduleCallback 根据当前时间和 priorityLevel 创建 Task。

获取当前时间 ​

Scheduler 通过 getCurrentTime 获取当前时间，作为计算任务时间字段和判断时间切片的基准：

  • 在支持 Performance API 的环境中，调用 performance.now，返回自当前上下文时间原点以来经过的高精度时间
  • 否则回退至 Date.now，通过记录初始时间并计算差值，得到相对时间
ts
const hasPerformanceNow =
  // $FlowFixMe[method-unbinding]
  typeof performance === 'object' && typeof performance.now === 'function';

if (hasPerformanceNow) {
  const localPerformance = performance;
  getCurrentTime = () => localPerformance.now();
} else {
  const localDate = Date;
  const initialTime = localDate.now();
  getCurrentTime = () => localDate.now() - initialTime;
}

SchedulerPriorities.js 定义了五个任务优先级：

ts
export const ImmediatePriority = 1;

export const NormalPriority = 3;
export const LowPriority = 4;

优先级越高，timeout 越短。例如 ImmediatePriority 的 timeout 是 -1，相当于任务进入队列时已经过期。确定 timeout 后，通过 expirationTime = startTime + timeout 得到过期时间：

ts
var timeout;
switch (priorityLevel) {
  case ImmediatePriority:
    // Times out immediately
    timeout = -1;
    break;
  case UserBlockingPriority:
    // Eventually times out
    timeout = userBlockingPriorityTimeout;   // 250
    break;
  case IdlePriority:
    // Never times out
    timeout = maxSigned31BitInt;   // 1073741823
    break;
  case LowPriority:
    // Eventually times out
    timeout = lowPriorityTimeout;   // 10000
    break;
  case NormalPriority:
  default:
    // Eventually times out
    timeout = normalPriorityTimeout;   //  5000
    break;
}

var expirationTime = startTime + timeout;

创建并入队 ​

时间字段计算完成后，创建 Task 对象。对于需要进入 taskQueue 的 Task，Scheduler 将 expirationTime 的值赋给 sortIndex，再调用 push 将其放入队列：

ts
var newTask: Task = {
    id: taskIdCounter++,
    callback,
    priorityLevel,
    startTime,
    expirationTime,
    sortIndex: -1,
};

// 以下是无延时调用路径；延时 Task 会进入 timerQueue
newTask.sortIndex = expirationTime;
push(taskQueue, newTask);

时间切片（Time Slicing） ​

优先级和任务队列决定下一个处理哪个 Task，时间切片则限制 Scheduler 一轮连续处理任务的时长，避免长时间占用主线程。每轮处理开始时，Scheduler 都会记录起始时间；每次准备执行尚未过期的 Task 前，再通过 shouldYieldToHost() 判断是否应当让出主线程。

通过异步接口安排宿主任务 ​

Scheduler 借助运行环境提供的异步接口安排宿主任务，并将每个宿主任务作为一轮工作的执行入口。以现代浏览器常用的 MessageChannel 为例，Scheduler 先注册消息回调，再发送消息来安排一次消息事件任务。

具体过程如下：

  1. 消息事件触发后，Scheduler 开始处理 taskQueue。
  2. 达到让出条件时，Scheduler 暂停本轮工作；如果队列中仍有 Task，便安排下一次消息事件。
  3. 当前消息事件结束后，浏览器有机会处理用户交互和渲染。
  4. 下一次消息事件触发后，Scheduler 继续处理剩余 Task。

说明： Scheduler 让出主线程，只是将控制权交还给浏览器事件循环。是否绘制取决于当前是否到达渲染时机以及页面是否需要更新；由于 Scheduler 不与帧边界对齐，因此也不保证让出前后属于不同帧。

根据运行环境的支持情况，Scheduler 依次选择以下异步接口：

接口使用环境优点缺点
setImmediateNode.js 和 IE运行环境支持时的首选：原因说明仅部分环境可用
MessageChannel现代浏览器避免 setTimeout 的嵌套延迟需浏览器环境支持 MessageChannel，在某些非浏览器环境中不可用
setTimeout最后的兼容性回退方案兼容性最好存在嵌套任务触发延时增加的问题：嵌套超过 5 层将被强制设为 4ms 最小超时；调度性能不稳定
ts
const localSetImmediate =
  typeof setImmediate !== 'undefined' ? setImmediate : null; // IE and Node.js + jsdom

let schedulePerformWorkUntilDeadline;
if (typeof localSetImmediate === 'function') {
  schedulePerformWorkUntilDeadline = () => {
    localSetImmediate(performWorkUntilDeadline);
  };
} else if (typeof MessageChannel !== 'undefined') {
  const channel = new MessageChannel();
  const port = channel.port2;
  channel.port1.onmessage = performWorkUntilDeadline;
  schedulePerformWorkUntilDeadline = () => {
    port.postMessage(null);
  };
} else {
  schedulePerformWorkUntilDeadline = () => {
    localSetTimeout(performWorkUntilDeadline, 0);
  };
}

判断是否让出主线程 ​

宿主任务开始执行后，Scheduler 会记录本轮的起始时间，随后开始处理任务队列。对于尚未过期的 Task，Scheduler 会判断是否应当让出主线程。

shouldYieldToHost() 用于判断 Scheduler 是否应当让出主线程。在 React v19.1.1 的稳定版本中，以下任一条件满足时，该函数返回 true：

  • 调用方已通过 requestPaint() 请求为浏览器绘制提供机会
  • 当前一轮的运行时间达到 frameInterval，其默认值为 5ms
ts
function shouldYieldToHost(): boolean {
  if (!enableAlwaysYieldScheduler && enableRequestPaint && needsPaint) {
    return true;
  }

  const timeElapsed = getCurrentTime() - startTime;
  if (timeElapsed < frameInterval) {
    return false;
  }

  return true;
}

调度流程详解 ​

前面分别介绍了任务入队和时间切片，本节将它们串联成一次完整的调度过程。调用链为：unstable_scheduleCallback → requestHostCallback → performWorkUntilDeadline → flushWork → workLoop。

下面按执行时序逐步展开。

第一步：unstable_scheduleCallback 将任务入队并触发调度 ​

Task 构造完成后的处理过程如下：

  1. 将 Task 压入 taskQueue。
  2. 通过 isHostCallbackScheduled 和 isPerformingWork 判断是否已经安排宿主回调或正在执行任务。
  3. 两者都为 false 时，将 isHostCallbackScheduled 设为 true，再调用 requestHostCallback() 启动调度。
ts
push(taskQueue, newTask);
// 如果当前既没有在调度中，也没有正在执行任务，才触发
if (!isHostCallbackScheduled && !isPerformingWork) {
  isHostCallbackScheduled = true;
  requestHostCallback();
}

这两个标志分别记录调度的不同状态，共同用于避免重复安排宿主任务：

  • isHostCallbackScheduled：已经安排了一次宿主回调，无需重复安排
  • isPerformingWork：当前正在执行任务，本轮结束后会自然继续调度

第二步：requestHostCallback 启动宿主任务循环 ​

requestHostCallback 是调度循环的启动入口，执行过程如下：

  1. 通过 isMessageLoopRunning 判断调度循环是否已经运行。
  2. 如果尚未运行，将 isMessageLoopRunning 设为 true。
  3. 调用 schedulePerformWorkUntilDeadline()，安排第一次执行 performWorkUntilDeadline。
ts
function requestHostCallback() {
  if (!isMessageLoopRunning) {
    isMessageLoopRunning = true;
    schedulePerformWorkUntilDeadline(); // MessageChannel / setImmediate / setTimeout
  }
}

第三步：performWorkUntilDeadline 执行一轮任务 ​

performWorkUntilDeadline 是每轮宿主任务的执行入口，执行过程如下：

  1. 清除上一轮的绘制请求标记。
  2. 获取当前时间，并将其记录为本轮的开始时间。
  3. 调用 flushWork 执行任务，并根据返回值决定后续操作：
    • 返回 true：表示仍有任务，在当前宿主任务结束前发起下一轮调度。
    • 返回 false：表示任务已处理完毕，将 isMessageLoopRunning 设为 false，结束调度循环。
ts
const performWorkUntilDeadline = () => {
  if (enableRequestPaint) {
    needsPaint = false; // 清除上一轮的绘制请求标记
  }
  if (isMessageLoopRunning) {
    const currentTime = getCurrentTime();
    startTime = currentTime; // 记录本轮起始时间，供 shouldYieldToHost 判断是否达到默认让出间隔

    let hasMoreWork = true;
    try {
      hasMoreWork = flushWork(currentTime);
    } finally {
      if (hasMoreWork) {
        schedulePerformWorkUntilDeadline(); // 还有任务，安排下一轮宿主任务
      } else {
        isMessageLoopRunning = false; // 没有任务了，消息循环结束
      }
    }
  }
};

第四步：flushWork 准备执行环境 ​

flushWork 围绕 workLoop 按以下顺序更新调度状态：

  1. 将 isHostCallbackScheduled 重置为 false。先前安排的宿主回调此时已经开始执行，不再处于“已安排、待执行”状态；重置该标志后，后续工作便可以在需要时发起新的调度。
  2. 将 isPerformingWork 设为 true，表示当前正在执行任务，避免执行期间重复触发调度。
  3. 调用 workLoop 处理任务。
  4. workLoop 退出后，通过 finally 将 isPerformingWork 恢复为 false，表示本轮执行已经结束，并确保异常时也能恢复状态。
ts
function flushWork(initialTime) {
  isHostCallbackScheduled = false; // 本次调度已开始，重置标志，允许后续任务再次触发调度

  isPerformingWork = true; // 标记正在执行，防止 unstable_scheduleCallback 重入触发新调度
  try {
    return workLoop(initialTime);
  } finally {
    isPerformingWork = false; // 无论成功还是异常，执行完毕后重置
  }
}

第五步：workLoop 在时间片内执行任务 ​

workLoop 会在一个时间片内循环处理 taskQueue，流程如下：

  1. 初始化时间：宿主任务开始执行时获取的时间会沿调用链传入 workLoop，作为 currentTime 的初始值。
  2. 读取堆顶 Task。
  3. 判断是否应当让出主线程：
    • 根据 currentTime 判断 Task 是否过期。
    • Task 尚未过期时，调用 shouldYieldToHost() 检查让出条件。
  4. 处理 callback：
    • callback 为 null 时，移除这个已取消的 Task。
    • callback 为函数时：
      • 执行 callback。
      • callback 执行结束后，重新获取当前时间并更新 currentTime。
      • 根据 callback 的返回值处理 Task：
        • 返回函数：该函数称为续体函数（continuation），将其保存回当前 Task，并结束本轮处理。
        • 未返回续体函数：移除已完成的 Task。
  5. 读取新的堆顶 Task 并重复上述步骤，直到让出主线程或队列为空。

Scheduler 无法中断正在执行的 callback，因此调用方需要将工作组织成可暂停、可恢复的多个片段。在 callback 内部，调用方不断检查是否应当让出主线程；需要让出时，停止当前处理并返回续体函数。Scheduler 将续体保存到原 Task，下一轮再继续执行剩余工作。

对应代码如下：

ts
let currentTime = initialTime;
currentTask = peek(taskQueue);
while (currentTask !== null) {
  // 任务尚未过期，且满足让出条件 → 让出主线程
  if (currentTask.expirationTime > currentTime && shouldYieldToHost()) {
    break;
  }

  const callback = currentTask.callback;
  if (typeof callback === 'function') {
    currentTask.callback = null;
    const didUserCallbackTimeout = currentTask.expirationTime <= currentTime; // 是否已超期
    const continuation = callback(didUserCallbackTimeout);
    currentTime = getCurrentTime(); // ⚠️ 刷新时间：callback 可能耗时较长

    if (typeof continuation === 'function') {
      // 任务未完成，返回了续体函数
      currentTask.callback = continuation; // 保留任务，下次继续执行
      return true; // 立即让出，不必等待默认间隔
    } else {
      // 任务完成，从堆中移除
      // ⚠️ 安全检查：防止 callback 执行期间任务已被移除导致重复 pop
      if (currentTask === peek(taskQueue)) {
        pop(taskQueue);
      }
    }
  } else {
    // callback 为 null，说明任务已被取消
    pop(taskQueue);
  }

  currentTask = peek(taskQueue);
}

if (currentTask !== null) {
  return true; // taskQueue 还有任务，通知外层继续调度
} else {
  return false; // taskQueue 已清空
}

Scheduler 在 React 中的作用 ​

理解 Scheduler 自身的任务、队列和时间切片机制后，再来看 React 如何使用这些机制。

React 如何借助 Scheduler 完成并发 render ​

React 的 Reconciler（协调器） 负责管理组件更新。一次更新主要经过两个阶段：

  • render（渲染阶段）：计算组件发生了哪些变化，不会直接修改页面；并发 render 可以暂停和恢复。
  • commit（提交阶段）：将计算出的变化应用到页面。这个阶段会修改 DOM，开始后必须同步完成。

如果组件树较大，一次完成所有 render 工作可能长时间占用主线程。React 因此将 render 拆分为一个个 Fiber 工作单元，使并发 render 可以在工作单元之间暂停。这里的“并发”不是多个线程同时执行，而是 React 可以分段完成 render，并为更紧急的工作让出执行机会。

React 与 Scheduler 的配合过程如下：

  1. React 根据更新优先级向 Scheduler 提交并发 render 的 callback；同步更新不经过这条调度路径。
  2. Scheduler 按优先级安排执行机会，并在获得执行机会后调用该 callback。
  3. React 在 callback 中逐个处理 Fiber 工作单元，并在每个工作单元前通过 shouldYield() 判断是否需要暂停。
  4. 需要暂停时，React 保存当前进度并返回续体函数；Scheduler 将续体保存到原 Task，下一轮再继续执行。
  5. render 完成后，React 进入 commit 阶段，将变更同步应用到页面。

调度其他工作 ​

除了并发 render，React v19.1.1 还会通过 Scheduler 安排部分非紧急工作，例如刷新 useEffect 等被动副作用以及清理缓存。

概括来说，React 决定要处理哪些工作、工作优先级以及可以在哪里暂停；Scheduler 负责创建和调度 Task，并提供是否应当让出主线程的判断。
